# VYNTRA — Shared Data Contracts & Interfaces

> **Purpose:** This document defines the shared data models, TypeScript interfaces, Firebase paths, and constants that all three parts must agree on. No part should deviate from these contracts without a formal proposal in `docs/shared-proposals/`.

---

## Firebase Collection Paths

All Firebase paths used throughout the platform are centralized in `src/shared/firebase/paths.ts`. No part should create ad-hoc collection names. The complete path structure is as follows:

The **user data** is stored under `users/{appId}` where `appId` is the unique application ID generated during authentication in the format `VYNTRA-USR-XXXXXXXX`. The user's profile information is stored as a subcollection document at `users/{appId}/profile`. The user's menstrual cycle records are stored at `users/{appId}/cycles/{cycleId}`.

The **shelter provider data** is stored under `shelter-providers/{shelterId}` where `shelterId` is in the format `VYNTRA-SHL-XXXXXXXX`. The shelter's occupant records are at `shelter-providers/{shelterId}/occupants/{personId}`. The shelter's facility records are at `shelter-providers/{shelterId}/facilities/{facilityId}`. The shelter's inventory items are at `shelter-providers/{shelterId}/inventory/{itemId}`, and each item's usage history is at `shelter-providers/{shelterId}/inventory/{itemId}/usage-log/{logId}`. The consolidated metadata document is at `shelter-providers/{shelterId}/metadata`.

The **service provider data** is stored under `service-providers/{providerId}` where `providerId` is in the format `VYNTRA-SVC-XXXXXXXX`.

The **order data** is stored under `orders/{orderId}` where `orderId` is in the format `VYNTRA-ORD-XXXXXXXX`.

The **World Chat data** is stored under `world-chat/{stateCode}/{districtCode}/current-record` for the active 6-hour period and `world-chat/{stateCode}/{districtCode}/completed-records/{periodId}` for past periods. The district code assignment and verification records are at `district-codes/{stateCode}/{districtCode}`.

---

## ID Generation Format

All IDs throughout the platform are generated using the shared `generateUniqueId(prefix)` utility from `src/shared/utils/id-generator.ts`. The function produces IDs in the format `VYNTRA-<PREFIX>-<8-character-alphanumeric>`. The prefixes used are: `USR` for user application IDs, `SHL` for shelter provider IDs, `SVC` for service provider IDs, `ORD` for order IDs, and `PRS` for person IDs generated by shelters when admitting someone who does not have an existing application ID. No part should use `Math.random()` directly or create IDs in any other format.

## Shared TypeScript Interfaces

The following interfaces are the data contracts that all three parts must follow. These are defined in `src/shared/types/` and must not be duplicated or modified within any part's folder.

### VyntraUser

This interface represents the core user identity created during authentication. It contains the `appId` (the unique application ID in `VYNTRA-USR-XXXXXXXX` format), the `googleUid` (the Firebase Auth UID from Google login), the `role` (which can be `user`, `shelter-provider`, or `service-provider`), the `createdAt` timestamp, and the `lastLoginAt` timestamp.

### UserProfile

This interface represents the complete user profile metadata. It contains the `appId`, `name`, `gender` (one of `male`, `female`, `other`, or `prefer-not-to-say`), `age`, `state`, `district`, `homeAddress`, `homeCoordinates` (an object with `lat` and `lng` number fields), and `emergencyContact`. For female users it optionally includes `pregnancyStatus` (an object with `isPregnant` boolean and optional `estimatedMonth` number), `disabilities` (an array of strings), `medicalConditions` (a string), `currentlyMenstruating` (a boolean), and `specialRequirements` (a string). It also contains `profileCompleteness` (a number from 0 to 100), `lastModifiedAt` timestamp, and `pendingSync` boolean indicating whether offline edits have not yet been synced to Firebase.

### CycleRecord

This interface represents a single menstrual cycle record. It contains `cycleId`, `userId`, a `startEvent` object (with `autoDateTime` timestamp and optional `editedDateTime` timestamp), an optional `endEvent` object (same structure), an optional `durationDays` number calculated from start to end, a `notes` array of `CycleNote` objects, and an `isActive` boolean that is true when the cycle has started but not yet ended. The `CycleNote` interface contains `noteId`, `content` string, `createdAt` timestamp, and optional `updatedAt` timestamp.

### ChatMessage and SixHourRecord

The `ChatMessage` interface represents a single World Chat message. It contains `messageId`, `userId`, `districtCode`, `category` string, `content` string, and `timestamp`. The `SixHourRecord` interface represents a 6-hour period record. It contains `recordId`, `districtCode`, `stateCode`, `periodStart` timestamp (one of the fixed boundaries: 12AM, 6AM, 12PM, or 6PM), `periodEnd` timestamp, `status` (either `active` or `completed`), `messages` array of `ChatMessage` objects, and `messageCount` number.

### ShelterProvider

This interface represents a registered shelter. It contains `shelterId` (in `VYNTRA-SHL-XXXXXXXX` format), `providerGoogleUid`, `shelterName`, `location`, `state`, `district`, `coordinates` (an object with `lat` and `lng`), `registeredMobile`, `totalBedCapacity`, `occupiedBeds`, `availableBeds`, `isActive` boolean, `registeredAt` timestamp, and `lastUpdatedAt` timestamp.

### ShelterMetadata

This interface represents the consolidated current state of a shelter. It contains `shelterId`, `shelterName`, `coordinates`, `registeredMobile`, `state`, `district`, `city`, `totalBedCapacity`, `occupiedBeds`, `availableBeds`, `currentOccupants` (an array of occupant summary objects with `personId`, `expectedStayDays`, and `admittedAt`), `facilities` (an array of facility summary objects), `inventorySummary` (an array of item summary objects with `itemName`, `currentQuantity`, and `requiredMinimum`), `shelterScore` (a number from 0 to 100, calculated by Part 3), and `lastUpdatedAt` timestamp.

### Occupant

This interface represents a person staying at a shelter. It contains `personId` (either an existing app ID or a shelter-generated ID in `VYNTRA-PRS-XXXXXXXX` format), `isExistingAppUser` boolean, `existingAppId` (optional, present when linking to an existing user), `shelterAssignedId` (optional, present when generated by the shelter), `admittedAt` timestamp, `expectedStayDays` number, `assignedBedNumber` (optional), and `status` (either `active` or `discharged`).

### InventoryItem

This interface represents an inventory item at a shelter. It contains `itemId`, `shelterId`, `itemName`, `currentQuantity` number, `requiredMinimum` number, `lastUpdatedAt` timestamp, and `usageRate` (optional number representing average daily consumption, calculated by Part 3's prediction system).

### UsageLogEntry

This interface represents a single usage record for an inventory item. It contains `logId`, `itemId`, `shelterId`, `quantityUsed` number, `associatedPersonId` (optional, present when usage was for a specific person), `usedAt` timestamp, and `notes` (optional string).

### ServiceProvider

This interface represents a registered service provider. It contains `providerId` (in `VYNTRA-SVC-XXXXXXXX` format), `providerGoogleUid`, `providerName`, `location`, `state`, `district`, `coordinates` (an object with `lat` and `lng`), `registeredAt` timestamp, and `isActive` boolean.

### Order

This interface represents a resource order from a shelter to service providers. It contains `orderId` (in `VYNTRA-ORD-XXXXXXXX` format), `requestingShelterId`, `requestingShelterName`, `shelterCoordinates`, `items` (an array of objects with `itemName` and `requestedQuantity`), `targetMode` (either `single` or `five-nearest`), `targetProviderIds` (array of provider IDs the order was sent to), `acceptedByProviderId` (optional, set when a provider accepts), `status` (one of `pending`, `accepted`, `preparing`, `dispatched`, `delivered`, or `confirmed`), `createdAt` timestamp, `acceptedAt` (optional timestamp), `dispatchedAt` (optional timestamp), and `confirmedAt` (optional timestamp).

### SOSRequest

This interface represents an SOS request generated by a user. It contains `userId`, `coordinates` (an object with `lat` and `lng`), `coordinateSource` (either `gps` or `profile`), `selectedConditions` (an array of condition code strings like `['PG', 'MD', 'WC']`), `compactCode` (the full encoded SOS string), `selectedShelterId`, `shelterMobileNumber`, `createdAt` timestamp, and `sentViaSMS` boolean.

## SOS Condition Codes

The following condition codes are defined in `src/shared/constants/sos-codes.ts` and must be used identically by Part 1 (encoding) and Part 3 (decoding):

`PG` means Pregnancy. `MN` means Menstruation. `VM` means Vomiting. `MD` means Medical Difficulty. `WC` means Wheelchair Required. `HC` means Healthcare Support Needed. `SN` means Sanitation Required. `AD` means Acute Distress. `CC` means Child Care Required. `EA` means Elderly Assistance.

The SOS code format is: `VYNTRA|<latitude>,<longitude>|<condition-codes-joined-by-dashes>|<userId>|<unix-timestamp>`. For example: `VYNTRA|26.9124,75.7873|PG-MD-WC|USR-A7K2M9X1|1696588800`.

## Shelter Scoring Weights

The scoring weights for calculating the Shelter Readiness Score out of 100 are defined in `src/shared/constants/scoring-weights.ts`. The weights determine how much each resource/facility category contributes to the overall score. The exact weight values can be tuned, but the initial distribution should cover: available beds, women's sanitation facilities, hygiene resources (sanitary pads etc.), healthcare facilities, wheelchairs and mobility equipment, medical-support equipment, and other emergency resources. Part 3 implements the scoring algorithm using these weights, and the weights themselves are shared so all parts can reference what contributes to the score.

## State Code Ranges

The state numerical code ranges for the World Chat district identification system are defined in `src/shared/constants/state-codes.ts`. Each state has a predefined numerical range (for example, one state might have 400–600 while another has 100–300). The ranges do not overlap between states. This file is the single source of truth for what numerical codes belong to which state, and Part 1's World Chat verification logic uses it to perform local validation before contacting Firebase.
